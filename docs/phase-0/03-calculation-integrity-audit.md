# Phase 0 · Calculation integrity audit

Python performs arithmetic in the engines below. Stage and connected adapters choose methods, map inputs and interpret missing coverage. Frontend dashboards select, aggregate for display and format saved results. Component tests verify several display invariants. This audit checks boundaries and existing executable tests. It does not certify sources, digitised curves, process designs or investment estimates.

### Numerical and approval findings

- **Approval boundary.** In [CAPEX runner](../../backend/blocks/capex/runner.py#L12) an unlocked AI proposal may be used in the same run. [Shared operating proposal](../../backend/blocks/shared.py#L88) can supply OPEX inputs. The resulting output is provisional but readily feeds Finance when calculation coverage is complete. Completeness is not an assumption approval. [Revenue](../../backend/blocks/revenue/runner.py#L15) explicitly checks authority and asks questions before calculation.
- **Missing versus zero.** Equipment may remain unpriced, causing incomplete whole-plant CAPEX despite a meaningful subtotal. Missing OPEX cash splits can coexist with known cash subtotal. Finance gates on complete CAPEX and OPEX. [Cashflow view](../../backend/blocks/cashflow/view.py#L95) can legitimately show only available revenue. These states require explicit export and UI labels.
- **Reproduction envelope.** Costs can carry source and price basis, and stage receipts hash inputs/outputs. The [fingerprint construction](../../backend/blocks/execution.py#L125) does not show a per-method implementation/code digest. The same saved input may yield a different estimate after a code/catalogue upgrade without changing its stored input fingerprint. [Monte Carlo service](../../backend/scenarios_and_uncertainty/monte_carlo/service.py#L13) separately hashes selected source modules and Garrett data. That narrower fingerprint does not solve method/version parity for ordinary stage receipts or all external data. Treat this as an inferred upgrade risk. Preserve old outputs and stamp new runs.
- **Scenario parity.** [Monte Carlo evaluate](../../backend/scenarios_and_uncertainty/monte_carlo/engine.py#L31) uses the connected adapter and can recompute a scenario-specific Revenue authority fingerprint after a recorded baseline approval. It extracts discounted payback under the generic key payback. Test authority preservation and output labels explicitly, including fixed and variable year mapping.
- **Partial coverage and source quality.** Source evidence, applicability constraints and provisional notices help identify risks. None demonstrates that an experimental or legacy cost curve is correct across its domain. Executed failures cluster at the unit/coordinate resolver, scoped price aggregation and the CAPEX handoff. A manual-price scenario also returned partial instead of complete. Independent references must establish whether each failure is an unsupported fixture, missing input contract or engine defect. See [baseline test record](06-testing-and-security-audit.md).

### Phase 1 handoff

Engineer 1 owns a versioned method registry and acceptance fixtures. Record method ID, source edition/page/table, permitted distribution, equation or digitisation approach, required roles and units, input range, factors, currency/period/scope, uncertainty, independent expected value, tolerance and reviewer. Engineer 2 agrees how the method and evidence IDs travel with persisted inputs and outputs. Benchmark datasets stay separate from pricing sources. A reconciliation failure opens a discrepancy with owner, evidence and release status rather than adjusting an oracle to match current output.
